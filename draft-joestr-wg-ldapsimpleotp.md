This document describes an additional authentication choice for the

# Introduction {#intro}

The Lightweight Directory Access Protocol ({{LDAP}}) is a
protocol for accessing directories. It offers searching, fetching,
and manipulating directory content and ways to access a set of
security functions.

The LDAP also offers to Login, or in LDAP terminology 'Bind operation', to
a given set of credentials.

These credentials are represented by the 'AuthenticationChoice' defined in
{{RFC4511}}.

According to this RFC, the scope of authentication is extended by a one-time
password (OTP) value to increase security by providing an additional authentication factor
that may vary based on the number of logins or time.

## Scope

This document defines the Simple OTP alternative of the LDAP AuthenticationChoice and how it is used in a Bind operation.

This document does not constrain how an OTP value is generated or verified, and it does not specify how OTP mechanisms are provisioned or how shared secrets are distributed.

## LDAP Bind request

The 'Bind request' is defined as follows in [(RFC 4511, Section 4.2)](https://www.rfc-editor.org/info/rfc4511/#section-4.2):

> BindRequest ::= [APPLICATION 0] SEQUENCE {
>   version                 INTEGER (1 ..  127),
>   name                    LDAPDN,
>   authentication          AuthenticationChoice }

## LDAP AuthenticationChoice

The 'AuthenticationChoice' is extendable according to
[(RFC 4520, Section 3.7)](https://www.rfc-editor.org/info/rfc4520/#section-3.7).

Each 'AuthenticationChoice' consists of an ASN.1 identifier in the form of a
keyword and a non-negative integer tag. Additional the method shall be classified
by the registrant
[(RFC 4520, Section 3.7)](https://www.rfc-editor.org/info/rfc4520/#section-3.7).

The scope of the 'AuthenticationChoices' are currently defined as:

> AuthenticationChoice ::= CHOICE {
>   simple                  [0] OCTET STRING,
>                           /* 1 and 2 reserved */
>   sasl                    [3] SaslCredentials,
>   ... }

## One-time password (OTP)

OTP value: A credential value presented by the client to the server, whose validity is limited, by number of uses or by time, as determined by the OTP mechanism in use. Examples are values generated by an HMAC-Based One-Time Password ({{HOTP}}) Algorithm or Time-Based One-Time Password ({{TOTP}}) Algorithm. This document does not require either.

OTP mechanism: The means by which OTP values are generated and verified. This document does not specify an OTP mechanism.

## Simple Authentication Method with OTP

The 'Simple Authentication Method with OTP', or short 'Simple OTP', is a way to
present the LDAP server a password and a OTP value.

The 'Simple OTP' as an 'AuthenticationChoice' is defined as:

> SimpleOTP ::= SEQUENCE {
>   password         OCTET STRING,
>   otpvalue         OCTET STRING }

The text-based password and OTP value transferred to the server using the
'Simple OTP' as an 'AuthenticationChoice' SHALL be transferred as {{UTF-8}}
encoded Unicode.

# Extending of LDAP AuthenticationChoices

This document extends the 'AuthenticationChoice' with a new alternative, Simple OTP, identified by the context-specific tag [4].

> AuthenticationChoice ::= CHOICE {
>   simple                  [0] OCTET STRING,
>                           /* 1 and 2 reserved */
>   sasl                    [3] SaslCredentials,
>   simpleotp               [4] SimpleOTP
>   ... }

# Classification

This document classifies Simple OTP as LIMITED USE, the same usage
that is assigned to the simple method in the IANA registry of LDAP
authentication methods
[here](https://www.iana.org/assignments/ldap-parameters#ldap-parameters-7).
This classification reflects that, for example, the connection to the LDAP
server must be secure to prevent leackage of credentials.

# Server Behavior {#server-behavior}

A server that implements this document MUST process a LDAP Bind request
with the Simple OTP alternative as follows:

1.  If Simple OTP is not enabled on the server, the server MUST
    return a BindResponse with the resultCode authMethodNotSupported
    ({{Section 4.2 of RFC4511}}).

2.  If the connection is not a protected connection, the server MUST
    reject the request with the resultCode confidentialityRequired
    and MUST NOT perform OTP verification.

3.  Otherwise, the server performs OTP verification for the entry
    named in the request.  OTP verification MUST fail for an OTP
    value that the server has accepted before.

4.  If OTP verification could not be performed, the server MUST NOT
    return success.  It returns the resultCode [to be decided].

5.  If OTP verification fails for any reason, including an invalid,
    expired, or previously accepted OTP value, or because the named
    entry does not exist or is not configured for Simple OTP, the
    server MUST return the resultCode invalidCredentials.

6.  If OTP verification succeeds, the server returns the resultCode
    success.  The server MUST record the OTP value as accepted before
    it returns success, so that two concurrent Bind requests with the
    same OTP value cannot both succeed.

# Client Behavior {#client-behavior}

A client that implements this document MUST observe the following
rules when it sends a LDAP Bind request with the Simple OTP alternative:

1.  The client MUST send the request only over a protected
    connection.  Before it sends the OTP value, the client MUST
    verify the identity of the server as specified in [RFC4513].

2.  If the client does not receive the resultCode success, it MUST
    NOT automatically retry the Bind with another authentication
    method, in particular with the simple alternative, unless the
    client has been explicitly configured to do so.  This applies
    to every outcome other than success, including
    authMethodNotSupported ({{Section 4.2 of RFC4511}}),
    invalidCredentials, protocolError, and a closed connection.

3.  Explicit configuration means a choice made by the user or
    administrator of the client.  A client MUST NOT treat
    information received from a server as such configuration.

# Implementation Considerations

The one-time password is opaque to the protocol defined in this document. A server could, for
example, verify it using {{HOTP}} or {{TOTP}}. This document does not require either.

# IANA Considerations {#iana}
